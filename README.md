### Reflections

1. **Consistency vs. Non-determinism:**
   Yes, every test produced the exact same outcome in all 5 runs for each judge. While LLMs are  non-deterministic, this behavior makes sense because the prompts were short and straightforward, simple capital lookup and binary `YES`/`NO`, which gives little room for different outcomes.

2. **Random vs. Systematic Judge Errors:**
   The judge errors were completely **systematic**, not random. Qwen's YES shows in the test result (True is not false), and print(verdict) later confirmed that llama replied "NO". Because the failure mode was constant in all 10 runs rather than different between attempts, it points to a systematic error.

3. **Isolating Model Errors from Judge Errors:**
   In `judge_accepts` and `judge_rejects`, the candidate answers (`"Stockholm"` and `"Bea City"`) are hardcoded rather than generated by `ask_capital`. Because the answering model is completely avoided in those tests, any failure can be attributed directly to the judge.

4. **"Right for the Wrong Reason":**
   `llama3.2:1b` passed `judge_rejects` in all 5 runs, which on paper looks like successful detection of a hallucinated city (`"Bea City"`). However, because it also answered `"NO"` to `"Stockholm"` in `judge_accepts`, it wasn't evaluating factual correctness, it simply output `"NO"` on every input. Relying on `judge_rejects` alone would have created a false sense of confidence.

5. **Implications for LLM-as-a-Judge in Practice:**
   A passing test is not proof of reliability and an LLM judge must be validated against a balanced set of known positive (true) and negative (false) cases to catch blanket `YES` or blanket `NO` biases.
   Model capability matters here. In our tests, small local models can easily answer simple factual questions (`ask_capital`), yet fail at tasks like judging another model's output. Observability is important: logging verdicts (print(verdict)) together with automated assertions shows why a test passed or failed.
